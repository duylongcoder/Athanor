# Phase 4: sprite atlases and particle VFX (audit)

Date: 2026-11-13. Sections 1, 3, 4 and 5 are the audit. Section 2 was updated after the atlases were built.

Scope: the owner asked for (1) sprite atlases to cut the number of items and the size, and (2) moving some VFX to
Particle System objects for performance. Tweening (PrimeTween), audio and fog are covered by another note.

The numbers come from the files on disk (PNG headers and pixels, `.meta` files) and from taking apart the last web
build, `Athanor/Build/web` (built 2026-11-12 22:47). The scripts used are in the scratchpad of this session. They are
described in section 4 so they can be rebuilt as a tool if wanted.

Short version:

- 209 sprite textures, 239 KB of PNG on disk, 1.62 M pixels, about 5.5 MB of uncompressed texture memory.
- In the download, the game art is about **0.28 MB of the 10.3 MB build (under 3%)**. The pixel art compresses to
  about 6% of its raw size. **Atlases will not make the download meaningfully smaller.** They will cut the texture
  count from 209 to 12 and should cut batch breaks. They add about 1 MB of texture memory because of empty space in
  the atlas pages.
- Bigger size wins turned up while measuring, outside the atlas work: the TextMesh Pro default font LiberationSans
  (about 0.52 MB compressed, unused by the game), the default skybox cubemap (0.1 MB) and the URP SMAA texture.
  See section 2.7.
- VFX: only `Sparks` is worth moving to a ParticleSystem. It peaks at about 150 to 200 live SpriteRenderers at
  60 Hz, and more on high refresh rate screens. Everything else should stay as it is. First, measure what the
  ParticleSystem engine module adds to the wasm. It is stripped from the current build.

## 1. Sprite inventory

### 1.1 Where sprites live and how they are found

- All sprites are under `Athanor/Assets/Art`. `Assets/Resources` holds only `content.json` and `layout.json`. No
  sprite is loaded through `Resources.Load`.
- `Editor/SceneBuilder.cs` (`BuildLibrary`) collects every `t:Sprite` under `Assets/Art` into
  `Assets/Art/ArtLibrary.asset`. It skips sprites that belong to a flipbook sheet, and it also collects the
  `FlipbookSheet` assets, the 4 TMP fonts and 3 materials (`lit` = URP Sprite-Lit-Default, `unlit` =
  Sprite-Unlit-Default, `glow` = `Art/Shaders/Glow.mat` with shader `Athanor/Sprite Glow`).
- At runtime `ArtLibrary.Sprite(name)` builds a `Dictionary<string, Sprite>` on first use and looks sprites up by
  name. `Make.Sprite/SpriteAt/Rect/Glow` call it through `Make.Lib`. The library is a serialized asset referenced
  from the scene (`GameFlow.library`), so every sprite is a **direct reference**. This matters for atlases (2.5).
- `Editor/SpriteImportRules.cs` forces every texture under `Assets/Art/` to: Sprite, 1 PPU, Point filter,
  Uncompressed, no mipmaps, alpha is transparency, Clamp, max size 4096, NPOT none, Single mode (unless a `.json`
  sits beside it), FullRect mesh, extrude 0, no physics shape.
- `Editor/FlipbookImporter.cs` slices pixelfx sheets in `Assets/Art/Fx/Sheets` (PNG + JSON written by
  `tools/fx/export.sh`) into Multiple-mode sprites and a `FlipbookSheet` asset per sheet. **That folder does not
  exist, and `ArtLibrary.asset` has `sheets: []`.** So `Fx.Spawn("implosion" | "holy-pillar" | "collect-burst" |
  "poof")` returns null today, and those four effects are absent from the game.
- The art itself is generated by `tools/art/export.mjs` (node). New art lands in the same folders.

## 2. Atlas plan (implemented 2026-11-13)

The proposal in the first version of this note (two atlases) was replaced by the owner's decisions below. The
rest of this section describes what was built. `Athanor/Assets/Editor/AtlasBuilder.cs` does it, and it can be
rerun at any time (idempotent: a second run leaves every file under Assets/Art unchanged).

### 2.1 Owner decisions (2026-11-13)

- Make the atlases for resource management, not for download size (the audit showed they do not shrink the build).
- Group by what the project uses the art for: UI, Background, item icons (materials), catalyst icons, aspect
  icons, event icons, Fx, bench/tiles, cutscene/props.
- Animation frames (flame_small_*, flame_big_*, liquid_*) are merged into one spritesheet per animation (Multiple

- Every texture stays uncompressed (RGBA32, set explicitly for Default, WebGL and Standalone), Point filter, no
  mipmaps, 2 px padding, no rotation, no tight packing, Include in Build on.

### 3.2 Pixel-art and rendering constraints for particles

- **Crisp squares.** PixelPerfectCamera renders into a 640x360 render texture (UpscaleRenderTexture), so a 1x1 world
  unit quad always rasterizes to exactly one pixel, wherever it is. Today the centre is rounded with `Mathf.Round`.
  The particle shader should do the same in the vertex stage: add the `Center` custom vertex stream, and set
  `pos = round(center.xy) + (pos.xy - center.xy)`. Then a 5x5 sparkle always lands on the same texel grid and
  motion steps in whole pixels as now. Use point-filtered textures and no rotation (`startRotation 0`,
  `alignment View`).
- **Sorting.** Everything is on the `Default` layer, ordered by `sortingOrder`. `ParticleSystemRenderer` takes
  `sortingLayerID` and `sortingOrder` like a SpriteRenderer, and the 2D renderer sorts it in the same queue. Ties at
  the same order (for example trail sparks at O+9 with the material glows at O+9) do not matter, because the glow
  blend is **additive** (`Blend SrcAlpha One`): the result is the same in any order.
- **Material.** The sparks use `Make.Lib.glow` today, which is unlit and additive, with `_Intensity` scaling the
  colour past the bloom threshold. `SpriteGlow.shader` reads `unity_SpriteColor` and `unity_SpriteProps`, which are
  set for SpriteRenderers only. Particles need a sibling shader, `Athanor/Particle Glow`, with the same blend,
  `vertexColor * _Intensity`, and the centre snap. Lit (Sprite-Lit) is not wanted: sparks are emissive.
- **HDR colours.** Callers pass colours like `new Color(2.2f, 1.7f, 0.6f)`, `colRes.Times(2.5f)` and
  `tint.Times(2.4f)`. That works now because sprite colour reaches the shader as floats. **Particle colours are
  Color32 and clamp at 1.** Fix: give the particle material a fixed `_Intensity = K` (K = 3 covers every current
  call; the largest is 2.5) and divide the colour by K at emit. 8 bits after dividing by 3 still leaves about 85
  steps for the dimmest colours. A test should assert that no call site exceeds K.
- **Bloom.** Unchanged if the HDR fix is in. Bloom threshold is 1.0, and the 2D renderer target is HDR.
- **WebGL GPU cost.** Additive 1-25 px quads add very little fill. The cost today is CPU per renderer. A
  ParticleSystem gives one draw per lane. ParticleSystem simulation runs on the main thread in WebGL (no worker
  threads), in native code. That is still cheaper than about 200 managed-to-native setter pairs plus 200 renderers.
- **Engine module size.** The current wasm has no native ParticleSystem module (only player-loop hook names,
  stripped by `stripEngineCode`). **The first ParticleSystem adds that module to `web.wasm`.** The cost is unknown
  and has to be measured (task 2). If it is large against the 10 MB budget, the fallback below gets the same draw
  call win without it.

### 3.3 Design: Sparks on ParticleSystems, same API

Callers stay as they are: `Sparks.I.Emit(pos, vel, color, life, order, gravity, sparkle, drag)`,
`Sparks.I.Burst(pos, count, color, speed, life, order, gravity, squash)` and `Sparks.I.Clear()`.

```
Sparks (MonoBehaviour on "Game", built by SceneBuilder as today)
  Dictionary<Lane, ParticleSystem> lanes   // made lazily, kept for the session
  struct Lane { int order; float gravity; float drag; bool sparkle; }
  Emit(...) -> lane = Get(order, gravity, drag, sparkle)
               lane.Emit(new EmitParams { position = pos, velocity = vel, startLifetime = life,
                          startColor = (color / K) as Color32, startSize = sparkle ? 5 : 1,
                          applyShapeToPosition = false }, 1)
  Burst(...) -> same random maths as now, calls Emit (so i % 4 == 0 still picks sparkle)
  Clear()    -> foreach lane: ps.Clear()
  LiveCount  -> sum of particleCount (for tests and the profiler overlay)
```

Why lanes: `EmitParams` cannot set gravity, drag, sorting order or sprite per particle. Those are system settings.
The current call sites use about 20-25 distinct (order, gravity, drag, sparkle) combinations: orders 30, 150, 151,
163, 171, 172, 301-312 and the UI ones; gravity values 60, 50, 40, 30, 20, 0, -2, -4, -6, -8, -14, -18, -20; drag is
0 for Emit and 1.5 for Burst. Each lane is one small GameObject. Only lanes with live particles draw.

Lane settings (built in code, like the rest of the scene; no prefab assets needed):

| Module | Setting | Matches today's |
|---|---|---|
| main | `simulationSpace World`, `playOnAwake false`, `loop false`, `startSpeed 0`, `gravityModifier 0`, `maxParticles 512`, `scalingMode Hierarchy`, `startRotation 0` | |
| emission, shape | disabled (emit by script only) | |
| forceOverLifetime | enabled, World, `y = -gravity` (constant, px/s²) | `vel.y -= gravity * dt`. Independent of `Physics.gravity` |
| limitVelocityOverLifetime | enabled, `limit = 1e6`, `drag = drag`, not multiplied by size or velocity | `vel *= 1 - drag * dt` (to verify, see the test in task 8) |
| colorOverLifetime | gradient: colour white, alpha 1 at 0, 1 at 0.5, 0 at 1 | `alpha * clamp01(life / maxLife * 2)` exactly |
| textureSheetAnimation | Sprites mode with one sprite (`sparkle` or `fx_dot` from the Fx atlas), or plain textures on two materials | |
| renderer | Billboard, `alignment View`, `sortingLayer Default`, `sortingOrder = order`, material `Particle Glow` (`_Intensity = K`), custom vertex streams Position, Color, UV, Center | |

Things that stay the same: randomness (same `Random` calls in Burst), the Emit and Burst signatures, the
`Sparks.I == null` checks in callers, and the timing of `Clear()` around cutscenes.

Fallback if the ParticleSystem module turns out costly: a "SparkMesh" backend behind the same API. One Mesh per
lane, rebuilt each frame from a struct array (`Mesh.SetVertexBufferData` with a float or half colour, so HDR is kept
without K, and positions rounded in C#), drawn by a MeshRenderer with `sortingOrder`. It gives the same one draw per
lane and adds no engine module. It costs more C# code than the ParticleSystem.

### 3.4 Implemented (2026-11-13): SparkMesh, time-based trails, loops

Owner decisions of 2026-11-13: move Sparks off one SpriteRenderer per particle with the same `Emit` / `Burst` /
`Clear` signatures; ParticleSystem only if it adds under about 300 KB compressed and looks the same, otherwise the
SparkMesh fallback; trails time based; Dust and the cutscene streams as loops; textures stay uncompressed.

**What was built**

- `Fx/SparkMesh.cs`: a batch of quads drawn by one MeshRenderer at one sorting order. Two submeshes: 1 px dots
  (`dot` at 0.25 scale, as before) and 5x5 sparkles, so at most two draws. Vertex colour is Float32 x4, so HDR
  colours (2.5 and so on) reach the shader unclamped; no K trick needed. Centres are rounded to whole pixels in C#
  (the same `Mathf.Round` as before) and the quad corners come from the sprite bounds, so a quad lands on exactly
  the pixels the SpriteRenderer covered. UVs come from `sprite.uv`, so it works when the atlas packs `dot` and
  `sparkle`. Index buffer is built once per capacity; per frame it writes one vertex buffer
  (`SetVertexBufferData`) and two submesh ranges. Fixed huge bounds, never culled. No allocation after growth.
- `Art/Shaders/ParticleGlow.shader` ("Athanor/Particle Glow"): the sibling of Sprite Glow. Unlit, same blend
  (`SrcAlpha One, One OneMinusSrcAlpha`), `texture * vertexColour`, `rgb *= _Intensity`, SRP Batcher compatible.
  Variant `CENTER_SNAP` snaps the ParticleSystem Center stream (only used by the define path).
  `Resources/ParticleGlow.mat` holds it (`_Intensity` 1, as `Glow.mat`) so it is in the build; `SparkMesh` makes one
  material instance per texture.
- `Fx/Sparks.cs`: particles are structs in one array per sorting order (a "lane"); one SparkMesh per lane. Same
  `Emit` / `Burst` / `Clear`, same `Random` calls in `Burst`, same integrator (`Step`) and fade (`Shade`). Simulates in
  `Update`, uploads in `LateUpdate` (after coroutines, so a particle emitted this frame shows where it was emitted;
  the old pool showed a reused sprite for one frame at its previous position). New: `LiveCount`, `LaneCount`,
  `Trail(...)`.
- `Fx/SparkParticles.cs`: the ParticleSystem lanes of 3.3, compiled only with `ATHANOR_SPARK_PARTICLES`.
- `Bench/Dust.cs`: the same closed-form loop (unchanged maths) drawn as one SparkMesh at order 8 instead of 46
  SpriteRenderers. `material` is kept as an unused field so the built scene still loads.
- `Cutscene/SimpleCutscene.cs`, `Update()` only, plus a private `Loop` class at the end: the ember (22/s, order 310),
  descent streak (70/s x strength, order O+1) and rune mote (26/s x strength, order O+3) streams are loops instead of
  `Sparks.I.Emit` calls. Each has rate x life slots; a slot is reborn every life at a hashed position and speed, and
  shows for that life only if the stream was on (with probability = strength) at its rebirth. So switching a stream
  on fills it from its source and switching it off lets the particles in flight finish, like an emitter. One
  SparkMesh each, parented to the story root.

**Trails, time based.** `Sparks.Trail(...)` takes the same arguments as `Emit` and emits `floor(dt * 60 + random)`
particles per call: exactly one per frame at 60 Hz, 2.4 times fewer per frame at 144 Hz, two per frame at 30 Hz (the
extra ones start part-way into their life so they spread out). The callers are in files this change does not own,
so they still call `Emit`. **To switch them on, change `Emit` to `Trail` on these lines** (one word each):
`GameFlow.cs` `Drawn` (`Sparks.I.Emit(p, ..., 0.25f, 151, 0, true)`), `Points` (both lines, orders 172 and 171),
`ToRack` (order 163), and `ReactionCutscene.cs` `Emit(from, to)` trail branch (order O+9). Rate-based callers
(TitleView, the post-burst rise in ReactionCutscene) are already time based and stay on `Emit`.

**Visual differences to look at**

- Embers, streaks and rune motes are now evenly spaced in time (a slot per 1/rate s) instead of Poisson random, and
  each reborn slot gets a fresh hashed position, so the stream reads the same but is slightly more regular. Their
  motion uses the closed form `p0 + v t - g t^2 / 2` (a fraction of a pixel from the old step integrator).
- When the descent ends the story root is hidden, so its streaks vanish with it instead of finishing their last
  fraction of a second over the bench. Rune motes still in flight fade out normally while `runeOn` ramps down.
- Sparks within one sorting order now draw in one mesh. The blend is additive, so the result is the same; only the
  alpha channel of the target (not shown) can differ.
- Dust: no change expected.
- Once the `Trail` swap is made: the reaction trails and the bench trails (drawn, points, to-rack) get the same
  density at 144 Hz as at 60 Hz (today they are 2.4 times denser on high refresh rate screens).

the SparksTests). The first full run had three SparksTests failures, both causes fixed in the code or test, not hidden:

- `Converting invalid MinMaxAABB` (logged as an assert, failed 2-3 tests). Cause, found from the stack trace in
  `Logs/Editor.log`: `Mesh.subMeshCount = 2` in `SparkMesh.Grow` derives each new submesh's bounding box from the
  mesh's box, which is invalid while the mesh has vertex storage (`SetVertexBufferParams`) but no vertex data and no
  box yet. It would have fired in a real session too, on the first `End()` of every lane. Fix: `Grow` now uploads the
  (zeroed) vertex array, sets `mesh.bounds` to the one huge box, and only then sets `subMeshCount`; each
  `SubMeshDescriptor` in `End` also carries that box (a default descriptor has an invalid one, and
  `DontRecalculateBounds` is on), and `mesh.bounds` is no longer set on the empty mesh in `Setup`. The log has zero
  `invalid MinMaxAABB` entries after the fix. No `LogAssert` was added.
- `Trail_EmitsTheSameDensity_AtAnyFrameRate(240)`: the test drew r from `System.Random(7)`, whose sampling spread
  (about one sigma of 30 particles over 20 s) was wider than the 3% tolerance. It now uses an evenly spread, deterministic
  r sequence (`frac(f * 0.618...)`), tolerance still 3% at 30, 60, 144 and 240 Hz. The code was unbiased.

## Risks

- **A SpriteAtlas defaults to compressed textures.** If any platform override is missed, the pixel art smears. Task
  3's test covers this.
- **Seams on stretched `dot` rects.** FullRect, extrude 0 and transparent padding may let a scaled-up rect sample a
  padding texel at its edge. Fixes: 4 px padding, extrude 1 on `dot`, or keep `dot` standalone.
- Texture memory grows by about 1.1 MB. Not a problem for WebGL at this size, but it is not "smaller".
- The ParticleSystem native module grows the wasm (task 2 measures it).
- Particle colours are Color32 (the K scheme). A future call with a colour above K would quietly lose glow.
- Lanes multiply if callers start passing many distinct gravity or order values. Cap them, or warn when there are
  more than about 40 lanes.
- Frame-rate-dependent emission already exists today. Keeping the API keeps it, and particles do not fix it.
- `SpriteGlow.shader` depends on sprite-only built-ins. Do not reuse it on particles without the sibling shader.
- The Sprite Atlas V2 cache can repack slowly in the Editor on first play. That is fine, but the first build after
  task 3 will take longer.
